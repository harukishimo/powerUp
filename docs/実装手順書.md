# powerUp 実装手順書

## 1. 目的

本書は、現在の要件定義書・デザイン仕様書・技術要件書・mockをもとに、Next.jsアプリを実装し、Google SpreadsheetとGemini APIを接続し、Vercelへデプロイできる状態まで進めるための手順を定義する。

実装対象は、今日のダッシュボード、朝食・昼食・夕食・間食の記録、スマートフォン利用、実際の成果、Geminiの採点案、直近7日間のデイリーログ振り返りである。

## 2. 実装前提

- `/Users/haruki.shimo/Documents/powerUp/mock/index.html`を視覚的な基準として残す
- `docs/`配下の文書を実装時の仕様の正とする
- Next.js App Router、React、TypeScriptを採用する
- DBは追加せず、Google Spreadsheetを唯一の保存先とする
- Gemini APIキーとGoogle認証情報はサーバー側の環境変数で管理する
- デプロイ先はVercelとし、Preview環境で確認してからProductionへ進める
- 個人の健康データを扱うため、認証またはVercelのアクセス制御なしに一般公開しない

## 3. 実装ルール

### 3.1 変更管理

- 作業開始前に既存ファイルとGit状態を確認する
- 既存のmockとdocsを削除・上書きしない
- 既存のユーザー変更と重なる場合は、変更範囲を分離する
- 1つのフェーズごとに、テスト可能な小さな変更として保存する
- 秘密情報をソースコード、ログ、スクリーンショットへ出さない

### 3.2 API発火ルール

`docs/API発火仕様書.md`に従う。

- 入力中はAPIを発火しない
- 保存ボタンでのみ`POST /api/logs`
- 日付変更時のみ`GET /api/logs/[date]`
- Geminiボタンでのみ`POST /api/ai/score`
- Sheets・GeminiのAPIキーはクライアントへ渡さない

### 3.3 採点ルール

`lib/scoring.ts`に純粋関数として実装する。Geminiへ総合点の計算を委ねず、AIは成果の採点案・理由・翌日の実験案だけを担当する。

## 4. フェーズ別実装手順

### Phase 0：現状確認と作業準備

#### 作業

1. `git status`で変更状態を確認する
2. `docs/要件定義書.md`、`docs/デザイン.md`、`docs/技術要件書.md`、`docs/API発火仕様書.md`を読む
3. `mock/index.html`をブラウザで確認する
4. Node.js、npm、Gitのバージョンを確認する
5. `.gitignore`に`.env*`、`.vercel/`、サービスアカウントファイルが含まれることを確認する

#### 完了条件

- 現在の変更を把握している
- 実装対象と対象外を説明できる
- 秘密情報を保存するファイルがGit管理対象外になっている

### Phase 1：Next.jsプロジェクト基盤

#### 作業

1. 既存のNext.jsプロジェクトがなければApp Router + TypeScriptで初期化する
2. `next.config`、TypeScript、ESLint、Prettierの基本設定を整える
3. `app/layout.tsx`でメタデータ、フォント、共通Shellを設定する
4. `app/page.tsx`、`app/logs/page.tsx`を作成する
5. `npm run dev`、`npm run lint`、`npm run build`を実行する

#### 成果物

- Next.jsアプリがローカルで起動する
- `/`と`/logs`が表示される
- `.env.example`が存在する

#### 完了ゲート

- mockの基本レイアウトをNext.jsで再現できる
- 既存のmockとdocsが壊れていない

### Phase 2：デザインシステムとUIコンポーネント

#### 作業

1. デザイン仕様書のカラー、タイポグラフィ、余白、角丸をCSS変数へ変換する
2. `AppShell`、`ScoreHero`、`MetricCard`、`TrendSummary`を作る
3. `SleepEditor`、`MealEditor`、`SnackEditor`、`PhoneEditor`、`ResultEditor`を作る
4. `GeminiInsightCard`、`DailyLogList`、`DailyLogDetail`を作る
5. 未入力、入力中、保存中、保存成功、エラーのUI状態を作る
6. 767px以下のモバイルレイアウトを確認する

#### 完了ゲート

- 4カテゴリとログ振り返りが画面上で確認できる
- 未入力と0点が異なる表示になる
- 主要ボタンがキーボードとモバイルで操作できる

### Phase 3：ドメイン型と採点ロジック

#### 作業

1. `types/domain.ts`に日次、食事、間食、AI提案の型を定義する
2. `types/api.ts`にAPIリクエスト・レスポンス型を定義する
3. `lib/validation.ts`にZodスキーマを定義する
4. `lib/scoring.ts`に睡眠・食事・スマホ・成果の採点を実装する
5. 未入力、0点、AI仮採点、ユーザー確定を状態として分ける
6. スコアバージョンを`v1`として固定する

#### テスト

- 睡眠スコア82が41点になる
- 食事は朝昼夕各8点、時間帯3点、間食3点で最大30点になる
- 集中時間の境界値が正しい
- 振り返り1〜5の変換が正しい
- すべて入力した場合に100点を超えない
- 未入力を0点に変換しない

#### 完了ゲート

- `npm run test`で採点テストが通る
- 同じ入力から同じ点数が再現される
- UIが採点関数の内部実装に依存しない

### Phase 4：Google Spreadsheet接続

#### 作業

1. Google Cloudプロジェクトを用意する
2. Google Sheets APIを有効化する
3. 個人利用MVP用のSpreadsheetを作成する
4. `daily_logs`、`meal_logs`、`snack_logs`、`ai_insights`タブを作る
5. 各タブの1行目に技術要件書のヘッダーを設定する
6. サービスアカウントを作成し、Spreadsheetをサービスアカウントへ共有する
7. `lib/sheets.ts`へサーバー専用のSheetsクライアントを実装する
8. 日次・食事のupsertと間食の追加・更新を実装する
9. 開発用Spreadsheetで読み書きを確認する

#### 完了ゲート

- ブラウザから認証情報が見えない
- 同じ日付を再保存しても日次行が増えない
- 食事区分を変えても別の食事として正しく保存される
- API障害時に入力内容がUIに残る

### Phase 5：API Routeと発火制御

#### 作業

1. `GET /api/health`を作る
2. `GET /api/logs`を作る
3. `GET /api/logs/[date]`を作る
4. `POST /api/logs`を作る
5. `clientRequestId`による冪等性を実装する
6. `POST /api/ai/score`のモックレスポンスを先に作る
7. 画面の保存ボタン、日付選択、AIボタンをAPIへ接続する
8. 入力中・保存中・成功・エラーの状態を画面へ反映する

#### 完了ゲート

- 発火仕様書の「発火させない操作」がAPIを呼ばない
- 保存1回につき、保存APIが重複発火しない
- 日付選択時に詳細が切り替わる
- APIレスポンスをZodで検証してから表示する

### Phase 6：Gemini API接続

#### 作業

1. `@google/genai`を追加する
2. `lib/gemini.ts`をサーバー専用として実装する
3. `GEMINI_MODEL`を環境変数から読む
4. 成果コメント、食事概要、決定的スコアを最小限のプロンプトへ変換する
5. 構造化出力で以下を返す

```json
{
  "achievementScore": 0,
  "confidence": "low | medium | high",
  "reason": "短い採点理由",
  "nextExperiment": "翌日に試すこと1つ"
}
```

6. Zodで型・範囲・文字数を検証する
7. 429、タイムアウト、不正JSON時に決定的採点へフォールバックする
8. ユーザーが採用または修正したときだけAI提案を保存する

#### 完了ゲート

- Gemini APIキーがクライアントバンドルに含まれない
- Geminiの失敗で通常の保存が止まらない
- AIの提案と確定値が画面上で区別される
- 1回のAIボタンで不要な複数リクエストが発生しない

### Phase 7：デイリーログ振り返り

#### 作業

1. `/logs`で直近7日の日付一覧を表示する
2. 日付、スコア、記録率を表示する
3. 日付選択で詳細APIを発火する
4. 4カテゴリの内訳を表示する
5. 食事・間食・成果コメント・AIの気づき・タイムラインを表示する
6. 未入力項目を「未記録」と表示する
7. 保存後に選択日を再取得して表示を更新する

#### 完了ゲート

- mockに追加したログ画面と同じ情報構造になっている
- 7日間の各日を選択できる
- 保存直後の変更がログ画面へ反映される

### Phase 8：テストとチームレビュー

#### 作業

1. 採点ロジックのユニットテストを実行する
2. APIの正常系・異常系テストを実行する
3. UIの主要ユーザーフローをPlaywrightで確認する
4. Blue Teamが実装品質・運用性を確認する
5. Red Teamが認証、API、プロンプト、データ漏えいを攻撃者視点で確認する
6. Purple Teamが検出結果と修正内容を突合し、再テストする
7. 重大度High / Criticalの指摘が0件になるまで修正する

#### 必須ユーザーフロー

```text
睡眠入力
  → 朝食・昼食・夕食の入力
  → 間食の入力
  → スマホ利用入力
  → 実際の成果・集中時間・振り返り入力
  → 保存
  → Gemini採点案
  → 採用または修正
  → ログ画面で確認
```

### Phase 9：Vercelデプロイ準備

#### 作業

1. `npm run lint`、`npm run test`、`npm run build`を通す
2. `.env.example`に変数名だけを記載する
3. 開発用・Preview用・Production用のSpreadsheetを分離する
4. VercelプロジェクトをGitへ接続する
5. VercelのEnvironment Variablesへ必要な値を登録する
6. Preview環境へデプロイする
7. `/api/health`、保存、ログ振り返り、Geminiの確認を行う
8. 本番アクセス制御を確認する
9. Productionへデプロイする

#### Vercel環境変数

```text
GEMINI_API_KEY
GEMINI_MODEL
GOOGLE_SHEETS_SPREADSHEET_ID
GOOGLE_SERVICE_ACCOUNT_EMAIL
GOOGLE_SERVICE_ACCOUNT_PRIVATE_KEY
APP_ACCESS_TOKEN
```

値はソースコードへ書かず、VercelのDevelopment / Preview / Productionを用途ごとに設定する。環境変数を変更した場合は、変更を反映するために再デプロイする。

## 5. 並列実装と依存関係

```text
Phase 0
  ├── Phase 1 基盤
  │     └── Phase 2 UI
  ├── Phase 3 型・採点
  │     └── Phase 5 API
  ├── Phase 4 Sheets
  │     └── Phase 5 API
  └── Phase 6 Gemini（Phase 5のAPI枠組み後）

Phase 2 + Phase 3 + Phase 4
  → Phase 5
  → Phase 7
  → Phase 8
  → Phase 9
```

Phase 2の静的UI、Phase 3の採点関数、Phase 4のSheetsアダプターは並列に進められる。ただしAPIとUIの接続は、型と発火仕様が確定してから行う。

## 7. 失敗時の戻り先

| 失敗 | 戻り先 |
|---|---|
| UIとmockの差異 | Phase 2、デザイン仕様書 |
| 点数が期待値と異なる | Phase 3、要件定義書の配点表 |
| シートに重複行ができる | Phase 4〜5、冪等性テスト |
| Gemini出力が表示できない | Phase 6、Zodスキーマとフォールバック |
| APIが不要に発火する | Phase 5、API発火仕様書 |
| 個人データが外部へ露出する | Phase 8、Red Teamレビュー |
| Vercelで環境変数を読めない | Phase 9、環境別設定と再デプロイ |
